## 一句话方案

两条**只动行为、不动布局**的修复：① 歌词取词不再「一次查不到就永久没有」——把 `(歌名, 歌手)`
展开成有序的候选查询（歌手别名 / 团体后缀 / 多歌手 / 歌名版本标注），瞬时故障（LRCLIB 的 503）
与「词库确实没有这条」严格分开（前者不写缓存、稍后自动重试一次），点歌词键时手上没有歌词就真的
去问一次；② 首页音乐块的**封面**成为「打开正在放歌的那个音乐软件」的入口（上游极简档本来就有
这个行为，音乐块被接管时漏了）。

## 背景与目标

**问题现状**（用户 2026-10-16 原话：「① 歌词的标志不管，打开也不显示歌词；② 点击音乐软件，要打开
对应的音乐软件」，并补充「歌词标志要起作用，显示歌词是之前实现过的内容，而且有的时候会显示」）。
逐条查证（工具：`mediaremote-adapter.pl get` 读实时会话、直连 `lrclib.net` 对照、`CGWindowList`
窗口探针）：

1. **取词只问一次，而且把失败当成「没有」**。`MusicManager` 原来只按 `(track_name, artist_name)`
   发一次请求，非 200 一律 `return []`，与「词库里确实没有」不可区分——而空数组**会被写进缓存**。
   实测对照组：从用户 LX Music 的 6 个歌单里随机取 30 首，用同一套查询参数直连 LRCLIB——
   **13 首无结果、8 首 HTTP 503（`ServerOverloaded`）、8 首有时间轴、1 首仅纯文本**
   （探针脚本见 §实际交付）。也就是说「一次查询」的命中率约 30%，而那 8 次 503 会被当成
   「这首歌没有歌词」缓存下来：用户再点歌词键也只会命中缓存、什么都不发生。
2. **字面量差一个字就查不到**。播放器报上来的歌手/歌名常带别名与版本标注，而 LRCLIB 按字面量过滤：
   实测「慕夏」的歌手是 `邓寓君(等什么君)`、词库里存 `等什么君`；「我也可以是流浪诗人」的歌手是
   `好妹妹乐队`、词库里是 `好妹妹`；「樱花(现场吉他版）」在词库里只有 `樱花`（而且上游给的
   开括号是半角、闭括号是全角）。这些歌**词库里明明有**，只是这条查询拿不到。
3. **首页音乐块的封面没有点击**。上游极简档的封面本来就会调
   `MusicManager.openMusicApp()`（`MinimalisticMusicPlayerView.albumArtButton`），音乐块接管
   （T5）时只搬了渲染、漏了这个动作；`openMusicApp()` 自身也只会 `openApplication`（对「窗口被
   藏起来放歌」的音乐软件不一定能把窗口带出来）。
   实测现场：用户的 LX Music（`cn.toside.music.desktop`）当时**只有一枚 122×128 的迷你窗在屏上、
   主窗口是隐藏的**——这正是「点了没反应」的典型形态。

**预期结果**：放一首词库里有词条的歌、岛保持不展开 → 屏幕上岛下方出现歌词；服务临时故障时不是
「这次没有就永远没有」，而是稍后自动再试一次（或点一次歌词键再问一次）；点首页音乐块的封面 →
正在放歌的那个音乐软件回到前台。

**关键约束**：不改首页布局与任何块的尺寸声明（docs/35 用户已拍板「现在的首页布局不需要动」，
docs/50 沿用）；不改歌词的**出口**（仍是 docs/35 的桌面悬浮层，面板里不显示歌词）；不新增第二个
歌词源（见 §明确不做）。

## 做法

0. **先问本机播放器自己的歌词缓存**（新增 `LxMusicLyricsCache`，`components/Music/`；用户 2026-10-16
   问「应用里面有歌词，为什么不显示，歌词不是从应用拿的？」）：
   - **系统不给歌词**：macOS 的 Now Playing（MediaRemote）载荷只有 title / artist / album / artwork /
     duration / 播放状态（本机实测载荷原文见 §取证），**没有歌词字段**——播放器界面里显示着歌词，
     别的应用看不到；
   - **但本机播放器自己存了**：LX Music（`cn.toside.music.desktop`）把歌词缓存在
     `~/Library/Application Support/lx-music-desktop/LxDatas/lx.data.db`（SQLite）：`my_list_music_info`
     是「id ↔ 歌名/歌手/时长」，`lyric` 表里 `type = 'lyric'` 的 `text` 是 **base64 的 UTF-8 LRC**。
     本机实测 984 首歌有主歌词，用户当时在听的「万水 / 李雨」正在其中；
   - **读取口径**：`SQLITE_OPEN_READONLY` + 300ms busy timeout（对方在写时会话让路）、**不写该库、
     不落临时文件**；匹配 = 归一化同名（复用 `LyricsQueryPlanner.normalizedKey`）+ 歌手互相包含，
     多条候选时优先**时长吻合**（`interval` 是 `mm:ss`）；只读 `type = 'lyric'`（翻译/音译不读）；
     任何失败（文件不在 / schema 变了 / 读被拒 / 库里没这首）一律答 `nil`，**静默回落 LRCLIB**——
     这层不抛错、不崩、不需要任何新权限（`Application Support` 不是 TCC 保护路径，
     与读通知库那条 FDA 不同）。
1. **候选查询阶梯**（新增纯逻辑 `LyricsQueryPlanner`，`components/Music/`）：
   `plan(title:artist:)` 产出**有序、去重、上限 5 条**的候选，**三档**各有各的问法与验法：
   - ① **原样**（恒在第一位且唯一）：歌名 + 歌手都是播放器报的原值，承载既有的 `bestLyricsMatch`
     打分匹配，**行为零变化**；
   - ② **歌手/歌名变体**：歌手串换写法（括号里的别名 / 去掉括号 / 去团体后缀
     「乐队·乐团·组合·合唱团·合唱队·工作室」/ 拆多歌手与 `feat.`）或歌名去掉尾部版本标注
     （最多两层；半角开 + 全角闭也能配）；顺序依据：中文歌的查不到更多来自**歌手串**；
   - ③ **只按歌名**（永远排最后，闸最松）：不带 `artist_name` 发请求，歌名取**剥掉版本标注之后**
     那个（词库存的多半是规范名）。这一档是为实测出来的那一类加的：同一首歌在词库里常常挂在
     另一种歌手写法下——「如果当时 / 许嵩」按歌手查空，词库里其实是繁体的 `許嵩` 与 `Xu, Song`
     （时长 316 / 314 / 317）；「丢了幸福的猪 (烟嗓版) / 穆菲菲」词库里是 `姜玉阳` 那一版。
   前面两档拿 `maximumQueryCount - 1 = 4` 条封顶，**给第 ③ 档留一个槽位**。
2. **两套接受闸**：
   - ② 档过 `accepts(...)`：**同名**（`normalizedKey` 相等，不是包含）+ **相关歌手**（归一化后
     互相包含）。`normalizedKey` = 小写 + 全角 ASCII → 半角 + 只留字母与数字（`许嵩、何曼婷` 与
     `许嵩&何曼婷` 因此相等）。**原样那条不过闸**——放行同名不同曲的代价实测过：「可乐」在词库里
     有 `半吨兄弟` 的版本，而用户听的那首 `赵紫骅` 词库里根本没有；
   - ③ 档过 `acceptsTitleOnly(...)`：**同名** + **时长吻合**（±3s）。时长是这一档唯一的
     身份凭据（LRCLIB 自己的 `get` 接口也拿歌名 + 歌手 + 专辑 + 时长做签名匹配）；只认歌名会
     拿回同名不同曲（实测「樱花」在词库里只有日语歌 `さくら`），只认时长毫无意义。
     **时长取不到（本机或词库任一侧为 0 / NaN / 负数）一律不放行**——宁可不出歌词，也不出一段
     没验过的歌词。同一首歌命中多条时**有 synced 的优先，其次时长最接近**。
3. **失败分类与重试节奏**（新增 `LyricsFetchPolicy`）：HTTP 状态码 → `ok`（200）/
   `transient`（408·425·429·5xx，值得重试）/ `permanent`（其余 4xx，按「没有这条」处理）；
   一次查询最多 `1 + 2 = 3` 次请求（0.7s / 2s），并带一个可识别的 `User-Agent`。
4. **瞬时故障 ≠ 没有歌词**：`fetchLyricsFromAPI` 在瞬时故障上**抛 `LyricsFetchFailure`**，
   调用方**不写缓存**、**不写「No lyrics found」**（那是「词库确实没有」的措辞），只把占位清空并记日志。
5. **一次延迟重试**：瞬时故障后 20s 自动再问一次（只一次，重试自己带 `allowTransportRetry: false`，
   不会自转成轮询）；切歌 / 关歌词时取消。
6. **点歌词键为什么就够了**：`handleLyricsPreferenceChange` **没有**加 `forceFetch`——D-04 那条
   （瞬时故障不写缓存）已经让「关掉再打开」自动落到取词路径（缓存里没有结论）。反过来，词库
   **确实没有**的歌（200 空数组）那份结论是可信的、可复用的，每次拨开关都重问一遍等于白打
   （最多 5 条候选）——重问不出来的还是问不出来，只是给公共免费词库添流量。
7. **整块 = 打开正在放歌的那个音乐软件**（`MusicModule.MusicHomeBlockView.body`）：命中区挂在
   最外层（两个 `.padding` 之后），点封面 / 曲名 / 留白 / `.none` 槽位都开播放器；块内两处自有
   手势**优先级更高、不受影响**——进度条是 `highPriorityGesture(DragGesture(minimumDistance: 0))`
   （点轨道 = 改播放位置，既有行为）、控制键各是一枚 `HoverButton`。指针变手（`NSCursor`，与
   `NotchColorPickerView` 同款）+ `.help` 提示（新键 `module.music.openPlayer`）。
   **为什么是「整块」不是「封面」**：第一版只把 36pt 的封面做成了入口，用户 2026-10-16 第二次
   反馈时圈的是**整块**（截图里那个框覆盖封面 + 曲名 + 进度那一带）并说「点击音乐区域，还是没能
   唤出音乐软件」；而那段窗口的日志里**连一条「打开音乐软件」都没有**——点击根本没进处理函数，
   即命中区太小（D-13）。
8. **`openMusicApp()` 两条路**：进程还在 → `activate(options: [.activateAllWindows])`；没跑 /
   激活被系统拒绝 → `openApplication(at:configuration:)`；拿不到 `bundleIdentifier` 时只记日志，
   不假装成功。全部走 `os.Logger(subsystem: "com.cmeng.gourd.music")`（原来是 `print`，
   GUI 里查不到东西）。

## 备选与取舍

| 备选 | 为什么不选 |
|---|---|
| 加第二个歌词源（网易云 / QQ 音乐的非官方接口） | 用户听的多是国产民谣/国风，LRCLIB 覆盖确实有限（实测 30 首里 13 首词库确实没有）。**2026-10-16 用户拍板：不加**——「没有歌词就不显示」（D-12）。本次的落点是：把「词库里其实有、只是挂在别的写法下」那批拿回来（做法 1 第 ③ 档） |
| 变体查询也走 `bestLyricsMatch` 打分（不加闸） | 变体放松了歌手串，不再钉住歌名就会拿回别人的同名曲（`可乐` 那条实测） |
| 原样查询也加同名闸 | 会**减少**既有命中（有些曲目的 trackName 写法与播放器报的不一致，而打分匹配本来能挑出最像的那条）；本次的原则是「只加不删」 |
| 缓存「没有这条」但不重试 | 就是现状：一次 503 让这首歌在本次运行里彻底静音 |
| 常驻轮询式重试（每 20s 一次直到成功） | 公共免费服务不该被当成本地缓存反复敲；一次足矣，用户还可以点歌词键 |
| 把歌词画回面板里（面板内歌词行） | 用户在 docs/35 明确选的「不占面板、屏幕上直接看」（本次反馈也没有要求改这一点） |
| 封面点击改成整块可点 | 整块里还有进度条（拖拽改播放位置）与五枚控制键，把「点一下空白 = 换前台应用」铺满整块容易误触；与前台应用块的「一格一动作」也不一致 |
| 用 `FrontAppSwitcher` 那套「激活 + 350ms 复检 + 补 reopen」 | 实测 `activate(.activateAllWindows)` 就够了（隐藏主窗口当场回来）；跨模块复用 `Modules/FrontApp` 的纯函数还会把「上游文件依赖模块文件」这条反向依赖带进来，不值当 |

## 明确不做

- **不新增歌词源**（LRCLIB 仍是唯一源）：用户 2026-10-16 明确「没有歌词就不显示」，所以不做第二个源，也不做任何「查不到就兜底显示别的」的路径（D-12）。
- **不改歌词的出口与显隐判据**：仍是「岛不展开 + 有活跃会话 + 拿到真实歌词行 + 未锁屏」（docs/35 D-07）。
- **不动首页布局、块尺寸、控制键配置**：本次唯一的视觉新增是封面上的指针与 tooltip。
- **不改 `bestLyricsMatch` 的打分口径**（原样那条逐字沿用）。
- **不清理上游既有的 `print`**：只把本次触及的取词路径换成 `os.Logger`。

## 已知限制

1. ~~封面关掉时没有入口~~ **已修**（D-13）：命中区是整块，与封面开关无关。
2. **LRCLIB 覆盖有限，且这是选定行为**：用户歌单的抽样里约 43% 的曲目词库**确实没有**
   （实测：`马尾姑娘 / 姜斌斌` 跨歌手 0 条、`不甘心的甘愿 / 邵帅` 0 条），这些歌不会出歌词。
   用户 2026-10-16 拍板「**没有歌词就不显示**」——不加第二个源，所以这是**已知且接受**的行为，
   不是待修项（D-12）。
3. **歌词只在岛收起时出现**（docs/35 口径）：在展开的面板里点歌词键，屏上**不会**立刻有变化——
   关掉面板（或让鼠标离开）才会看到悬浮层。这是设计口径，不是本次的缺陷；面板内歌词是另一件事。
4. **动态封面（live canvas）那一档的命中未上屏复核**：图形摘出命中链是代码层的兜底，
   现场只验过静态封面（LX Music 的专辑图）。
5. 取词的 3 次请求是**串行等待**，没有进度反馈（悬浮层在拿到真实歌词行之前不出现）。
6. **本地歌词缓存只覆盖「在 LX Music 歌单里的歌」**（映射表就是歌单表；本机 `music_info_other_source`
   为空），且认的是 **LX Music 的默认数据目录**（用户若在 LX Music 里改过数据目录就找不到，回落
   LRCLIB）；这一层是**为 LX Music 写的**，别的播放器没有对应缓存。schema 一旦被上游改掉，
   本层静默失效（不崩、回落 LRCLIB）。
7. **歌词只在岛收起时可见**（老口径，见上一条 3）——**这一条是「看不到歌词」最常见的误判来源**：
   面板展开着的时候，桌面歌词层是**隐藏**的；用户 2026-10-16 的两次「不显示」都发生在这个状态下。

**取证（本机实测，2026-10-16）**：

- 实时会话：`mediaremote-adapter.pl <framework> get` → `bundleIdentifier cn.toside.music.desktop`、
  `title 樱花(现场吉他版）`、`artist 茶季杨`、`album 樱花`。
- LRCLIB 覆盖抽样（30 首，脚本见下）：13 无结果 / 8 有时间轴 / 1 仅纯文本 / 8 HTTP 503；
  变体对照：`樱花` + `茶季杨` → 200 空数组、只用歌名 → 5 条（都是**别人的**同名曲，故必须过同名闸）；
  `慕夏`（歌手 `邓寓君(等什么君)`）→ 空，换 `等什么君` → 5 条命中；`我也可以是流浪诗人`
  （`好妹妹乐队`）→ 空，换 `好妹妹` → 2 条命中。
- **本机播放器歌词库**（2026-10-16 17:0x）：`lyric` 表 984 首有主歌词（`tlyric` 151 /
  `rlyric` 22，且 0 首是「只有 lxlyric/tlyric 而没有 lyric」）；`万水` 的映射行 =
  `wy_424057089 | 万水 | 李雨 | 02:58`，`lyric` 行解出来正是用户播放器界面上的逐行；
  `music_info_other_source` 为空。

## 决策摘要

| 编号 | 决策 | 依据 |
|---|---|---|
| D-01 | 歌词的出口与显隐判据不动（仍是 docs/35 的桌面悬浮层，只在岛收起时出现） | 用户 2026-10-10 的明确选择；本次反馈是「按钮不管用」，不是「要画回面板」 |
| D-02 | 候选查询阶梯：原样 → 歌手/歌名变体 → **只按歌名**，含原样最多 5 条 | 实测的三类字面量差异；公共免费词库不该把重试当默认策略 |
| D-03 | 原样那条**不加闸**（沿用打分匹配），只有变体过「同名 + 相关歌手」闸 | 只加不删：既不减少既有命中，又不让变体拿回别人的同名曲 |
| D-04 | 瞬时故障（网络 / 超时 / 408·425·429 / 5xx）**不写缓存、不写「No lyrics found」** | 「这一次没问出来」与「词库没有这条」是两回事，混在一起就是本次的根因 |
| D-05 | 瞬时故障后**自动重试一次**（20s，不算轮询） | LRCLIB 的 503 是秒级抖动；用户不必为此去点歌词键 |
| D-06 | **不为开关加 `forceFetch`**：瞬时故障不写缓存这条已经让「关掉再打开」变成一次真查询；词库「确实没有」的结论可复用 | 「打开按钮要有反应」的字面要求由 D-04 满足；对公共免费词库不做无谓重问 |
| D-07 | 首页音乐块的**封面**= 打开正在放歌的那个音乐软件（含指针变手 + `.help`） | 上游极简档既有行为（T5 接管时漏搬）；封面是块里唯一代表「哪个软件」的元素 |
| D-08 | `openMusicApp()`：在跑 → `activate(.activateAllWindows)`；否则 → `openApplication` | 实测隐藏主窗口能被 activate 叫回来；没跑的情况才需要 LaunchServices |
| D-09 | 新增一条本地化键并**登记进** `tests/test_general_ai_configuration.py` 的 `LOCALE_KEYS` | 那份守卫的契约就是「catalog 的每一处改动都要登记」 |
| D-10 | 取词失败一律进 `os.Logger`（subsystem `com.cmeng.gourd.music`） | 原来只有 `print`，「点了没反应、日志里也没有」是最难查的状态 |
| D-11 | 第三档「**只按歌名 + 时长 ±3s**」（`acceptsTitleOnly`）；本机或词库任一侧时长取不到就不放行 | 用户反馈「重启后还是不管用」时实测出来的：`如果当时 / 许嵩` 在词库里是繁体的 `許嵩`/`Xu, Song`，`丢了幸福的猪 (烟嗓版)` 在词库里是 `姜玉阳` 那一版——只认歌手串会把这批全判掉；时长是同名之外唯一可验的身份凭据 |
| D-12 | **不加第二个歌词源**（LRCLIB 仍是唯一源）；词库没有的歌就不显示 | 用户 2026-10-16 原话「没有歌词就不显示」 |
| D-13 | 「打开播放器」的命中区从 36pt 封面**扩到整块**（进度条与控制键除外） | 用户第二次反馈圈的是整块；且那段窗口的日志里没有任何「打开音乐软件」记录——点击没进处理函数，就是命中区太小。同级的前台应用图标格在同一个面板里可点（既有实测），说明块内 tap 本身没问题 |
| D-14 | 歌词取词**先读本机播放器（LX Music）的本地歌词缓存**，取不到再走 LRCLIB | 用户问「歌词不是从应用拿的吗」；系统不给歌词（Now Playing 载荷无歌词字段），但该播放器自己把歌词存在本地 SQLite 里，离线、与它界面上显示的逐行一致，且不需要新权限 |
| D-15 | `parseLRC` 提成纯函数 `LyricsTextParser`，并修两处解析错：**小数位 1～3 位**（原来只认 1～2 位，`[00:06.100]` 这种毫秒时间轴整行被丢）与**一行多标签**（原来只认第一个，后面的标签残留在文本里） | 真数据实测：本地缓存里「不知归期的故人」27 行只解出 5 行、「揪心的玩笑与漫长的白日梦」修复前后 9 → 29 行；这两处都是上游老错，以前没喂过这类词条 |
