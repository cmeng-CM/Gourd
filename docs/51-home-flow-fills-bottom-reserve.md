## 一句话方案

首页**底部**那 20pt 宿主内边距（`NotchHomeView` 下侧 8 + `ContentView` 底边 12）：接缝用一条**负
底部内缩**把它整份交给可变流（内容区多拿 20pt），流的**末行**只长高 **12pt**（= 20 − 8），
**余下 8pt 作为板底与面板下缘之间的一条缝留着**——两块因此比改前高 12pt、通知列表多露出第 7 条
的标题行，同时不贴边。**面板高度与高度账本一个字没动**：变的只是「这 20pt 由谁用掉」。

## 背景与目标

**现象**（用户截图）：首页最下面一条横带是空的——通知块与今日块的内容在 413.5pt 附近就结束了，
面板下缘在 444pt，中间约 24pt 是空玻璃（再往下 18pt 是窗口的阴影带）。

**几何成因**（2026-10-16 实测，工具 `CGWindowList` + `screencapture` + 逐行亮度剖面）：

| 量 | 实测值 | 出处 |
|---|---|---|
| 面板窗口 | 1126 × 466pt | `CGWindowListCopyWindowInfo` |
| 可见黑框下缘 | 444pt（= 窗口底 462 − 阴影带 18） | 全宽一条硬边（亮度 40 → 12） |
| 两块板的底 | ≈424pt | 板缘台阶（块内比缝暗 2–8/255） |
| 空的一截 | **20pt**（+ 阴影带 18pt 看起来也像面板的一部分） | 444 − 424 = 20 = `NotchHomeView` 8 + `ContentView` 12 |

**为什么 `auto` 档还留得下这一截**：auto 的等式是「面板高 = 内容自然高 + `homeVerticalPadding`
（40）」，而内容自然高只由**块的申报高**决定（通知 225 / 今日 228 → 行高 228）。40 里那 20pt
（`NotchHomeView` 下侧 8 + `ContentView` 底边 12）落在内容之外，面板贴住内容的同时也就把这 20pt
留成了空玻璃——其它页是「量出来填满」的，只有首页是按申报高排的，所以这条留白只在首页看得见
（用户报的也正是首页）。

**目标**：把这段留白交给首页下缘那两块（通知 / 今日），并保证

1. **面板高度不变**（用户没要求面板变高变矮；实测改后窗口仍是 1126 × 466）；
2. **账本口径不变**（`homeVerticalPadding` 仍是 40、`contentHeight(from:)` 仍只算申报高之和 +
   两带 + 表头）——否则 `auto` 会「内容高 + 40」把面板推着涨，与上一条冲突；
3. 顶部的 8 + 出血 4 + 表头↔内容的缝 8 **不动**（它们不是「面板下缘的留白」）；
4. **不贴边**（第二轮反馈）：两块板底与面板下缘之间留一条缝——贴边那版实战看下来「太满」：
   板的圆角撞上面板的下圆角、通知列表最后半行直接切在面板边上像被裁掉。

## 做法

三处改动 + 一条口径，链起来：

1. **接缝把 20pt 让给流**（`HomeStripView.swift` 的 `HomeBandedHomeView`）：
   在 `GeometryReader` 上挂一条 `.padding(.bottom, -PanelAutoHeight.homeFlowBottomCredit)`。
   负内缩让内容区**多拿**这 20pt（SwiftUI 的 padding 提案是「父提案 − inset」，inset 为负即放大；
   已用真视图探针钉过：宿主给 200 → 几何报 220），多出来的一段正好落在那两处**透明**内边距上，
   裁剪仍只由面板的 `clipShape` 做。
   **为什么不把那两处 `.padding` 改成 0**：`ContentView` 的底边 12 是**所有页共用**的，还给其它
   tab 的「量高 → 面板高」换算当基准（`panelVerticalPadding = 12 + 4 + 8`）——改成 0 会让那些页
   的换算失去基准（量出来的自然高每轮缩 12，收敛变成一路缩到下界）。改动只落在首页这一支上。

2. **流算末行长高**（`HomeFlowLayout.plan(…:lastRowStretchLimit:)`，新参数，缺省 0）：
   可用高有富余时，**最后一行**长高吃掉它（行高 = 该行申报高 + 吃到的量），上面的行一律保持申报高；
   吃到的量 `min(富余, 上限)`，上限 = `PanelAutoHeight.homeFlowBottomAbsorbed`（**12**）。
   **为什么要有上限**：手动高度档下面板可能比内容高出几百 pt，那是用户选的框、不是「留白」，
   不该被块吃掉；上限也让两条调用路径的差别只剩这一个数——**账本那一份必须用缺省 0**
   （拿开着的 plan 去写账本，末行会被撑到预算上限、面板跟着涨到上界；有专门用例钉住这点）。

3. **两个常数与出处**（`PanelAutoHeight`，各处唯一取值）：
   - `homeFlowBottomCredit = 8 + 12 = 20`：让给流的那一份（负内缩用它）；
   - `homeFlowBottomGap = 8`：其中**留缝**的一份（D-09，用户选定）；
   - `homeFlowBottomAbsorbed = credit − gap = 12`：末行**实际长高**的量（唯一算式，接缝传的就是它）。

链上的数字（本机实测那一档）：

| 环节 | 改前（缝 20） | 贴边版（缝 0，已否） | **定稿（缝 8）** |
|---|---|---|---|
| 面板高（窗口 / 可见黑框） | 448 / 444（窗口 466） | 同左（**逐字不变**） | 同左（**逐字不变**） |
| 内容区高 | = 两带 + 流（零富余） | +20 | +20 |
| 流那一行（= 两块） | 228（申报高） | 248 | **240** |
| 通知块视口 | 203（6 行整） | 223 | **215（6 行 + 第 7 条的标题行）** |
| 通知列表最后一条文本的底 | **412.5pt** | 439.5pt | **431.0pt** |
| 今日块行数预算 | 6 | 6（`scheduleRowCount` 封顶） | **6** |
| 板底 → 面板下缘 | 20pt 空玻璃 | 0（贴边） | **8pt 缝** |

## 接口与数据形状

```swift
// PanelAutoHeight（sizing）
static let homeFlowBottomCredit: CGFloat = 8 + 12          // 20：让给流的那一份（负内缩用它）
static let homeFlowBottomGap: CGFloat = 8                  // 8：其中留缝的那一份（D-09）
static var homeFlowBottomAbsorbed: CGFloat { credit - gap } // 12：末行实际长高的量

// HomeFlowLayout（Host）
public static func plan(
    items: [Item],
    availableWidth: CGFloat,
    availableHeight: CGFloat,
    metrics: Metrics,
    lastRowStretchLimit: CGFloat = 0   // 末行最多长高多少（0 = 不吃，逐字是改动前的行为）
) -> Plan
```

`Row.height` 的口径：**末行**（`rows.last`）= 该行申报高 + 吃到的量；其余行 = 申报高。
`Plan.heightUsed` 随之含这一份（接缝给流钉的 frame 与它一致）。缝不参与任何算式——
它就是「可用高里剩下、没人用掉的那 8pt」，落在流的 frame 之下、面板的下边距里。

调用点三条（**只有第二条带上限，且用 `homeFlowBottomAbsorbed`**）：

| 调用 | `lastRowStretchLimit` | 用途 |
|---|---|---|
| 接缝「画出来的那一份」 | `homeFlowBottomAbsorbed`（12） | 面板多高就画多满 |
| 接缝「账本那一份」（`naturalFlowBudget` 下） | 缺省 0 | 内容自然高 = 申报高之和 |
| 用例（`HomeStripLayoutTests`） | 与接缝同一条 | 渲染真值的镜像 |

## 备选与取舍

| 备选 | 为什么不选 |
|---|---|
| **缝 = 0（贴边）**：把让出的 20pt 全给流 | **用户已上屏否掉**（「太满、视觉效果很差」）：板圆角撞面板下圆角；通知列表那半行直接切在面板边上看不出是「还有内容」还是「被裁了」。真实截图见 §实际交付 |
| **缝 = 20（= 改前）** | 等于什么都没做：用户第一轮反馈的那条留白原样还在 |
| **缝取别的值**（如 12 / 16） | 8 是用户在 0 / 8 / 20 三档之间挑的；12 以上开始接近「没变化」，4 又回到「贴边感」。要改就改 `homeFlowBottomGap` 一个数（缝与块的增量同时联动） |
| **把两块申报高直接加 12**（通知 237 / 今日 240）+ 账本减 12 | 账本要被塞一个「减去宿主内边距」的魔数，且申报高是**模块的**自我描述——它不该知道宿主的底部留白；让出方留在宿主一侧 |
| **把 `homeVerticalPadding` 直接改成 28** | 它是**所有页**的换算基准：其它页的自然高是量出来的（量到的是「面板高 − 表头 − 24」），基准缩 12 → 每轮量出来再缩 12 → 收敛变成一路缩到下界（120） |
| **负内缩改成「改那两处 `.padding` 为 0」** | 见 §做法 1：`ContentView` 的底边是所有页共用的 |
| **末行「有多少富余吃多少」不设上限** | 手动高度档下面板比内容高出几百 pt，两块会长成一整屏的大板——那不是「填留白」 |

## 明确不做

- **不动顶部**（`NotchHomeView` 上侧 8、顶出血 4、表头↔内容的缝 8）：不是「面板下缘的留白」。
- **不动窗口的阴影带 18**：它在面板黑框**之外**（窗口 = 黑框 + 18），不是内容能填的区域；
  改它等于改面板的投影观感，与本次反馈无关（用户截图里红框的下半段其实是它）。
- **不给块加「吃掉剩余空间」的通用钩子**（`homeBlockAbsorbsSurplus` 的竖向对照）：本次只有一处
  需要，且上限固定，加钩子要动 manifest / 注册表 / 设置页，收益不值。
- **不改块的内部行数上限**：今日块的 `maximumScheduleRows = 6` 与通知块的视口语义都没动——
  本次只改「块有多高」，不改「块里放几行」。

## 已知限制

1. **末行只是「变高」，不是「内容变多」**：今日块的行数仍钳在 6（`scheduleRowCount`），只有 1 条
   日程时多出来的 12pt 是**板的空白**；通知块是滚动视口，因此真的多露出第 7 条——**标题行可见、
   正文行被视口切掉**（定稿实测：最后一条文本止于 431.0pt = 第 7 条的标题被切了一点点）。
   这是滚动器的既有语义（半行 = 「下面还有」的信号），不是缺陷。
2. **末行里有形态档高的块时它也会被拉高**（镜子这类「尺寸 = min(宽, 行高)」的块）。这是既有现象
   的延续：行高本来就已经是「行内最高块」的函数（镜子与今日块同处一行时它的直径早就跟着行高走），
   本次只是把行高再抬高 12pt。用户当前配置里首页流只有通知 + 今日（都申报固定高），不受影响。
3. **面板比内容矮时富余为 0，本条不生效**：流被整行丢掉时末行照样长高（吃的是「丢掉那行留下的
   空」，上限 12pt），但不会有别的影响；一行都没画时没有末行，富余无处可去（留空）。
4. **`homeFlowBottomCredit` 是字面量 `8 + 12`**：`NotchHomeView` 的 `.padding(8)` 与
   `ContentView` 的 `.padding([.horizontal, .bottom], 12)` 若改了数值，这个常数要跟着改
   （与 `homeVerticalPadding` 那张表同一个纪律：逐项写死 + 注释指出处，没有编译期联动）。
5. **缝是「剩下没人用」的 8pt，不是一个被画出来的东西**：它由「让出 20 − 吃掉 12」推出来。
   若哪天流的末行吃不满（例如富余不足 12），缝会比 8pt 大——这是设计内的（缝是上限的另一面）。

## 决策摘要

| 编号 | 决策 | 依据 |
|---|---|---|
| D-01 | 首页**底部**那 20pt（`NotchHomeView` 8 + `ContentView` 12）归可变流；顶部各项、阴影带 18 一律不动 | 用户 2026-10-16 要求「铺满首页下面这条留白」；实测那 20pt 正是「板底 → 面板下缘」的距离 |
| D-02 | 用**负底部内缩**在首页这一支把 20pt 要过来，不改共用的 `.padding` | `ContentView` 的底边 12 是其它 tab 的换算基准（改了会让那些页一路缩到下界）；负内缩只影响首页的几何 |
| D-03 | 高度账本与 `homeVerticalPadding`（40）**逐字不动**，面板高度因此不变 | 用户只要求「内容填满」，没要求面板变高；账本一动，auto 会「内容高 + 40」把面板推着涨 |
| D-04 | 由流的**末行**长高吃掉这份富余（`lastRowStretchLimit`），且**有上限** | 「填下缘的留白」= 最后一行的责任；上限让手动高度档下多出来的几百 pt 不被吃掉，也让两条调用路径只差一个数 |
| D-05 | 账本那一份调用固定用缺省 0（并有专门用例钉住） | 拿长高的 plan 写账本 = 把「这一帧面板多出来的一段」写进「内容自然高」，面板会被推着涨到上界 |
| D-06 | 不把两块的申报高直接加 | 申报高是模块的自我描述，不该内置宿主的底部留白；让出方留在宿主一侧 |
| D-07 | 块的内部行数上限（今日 6 行、通知视口语义）不动 | 本次只改「块有多高」，不改「块里放几行」——两件事混在一起会让行为不可解释 |
| D-08 | 先按「让出的 20 全给流（缝 0）」实现并上屏 | 先满足用户字面要求（铺满），再让他在真机样张上判断要不要留缝——比在描述里争论「留多少」便宜 |
| D-09 | **留 8pt 缝**：末行只长高 12pt（= 让出的 20 − 缝 8） | 用户 2026-10-16 上屏复核后否掉贴边版（「太满、视觉效果很差」），在三档（0 / 8 / 20）样张间选定 8 |
| D-10 | 三个量各有一个名字（`credit` / `gap` / `absorbed`），末行长高的量由 `credit − gap` **算**出来 | 让出多少、留多少、吃多少是一件事的三个面；写死两个数迟早互相矛盾 |
